CleverStudy

A study platform where a PDF becomes topics, a practice quiz, flashcards and a chat assistant that answers from the document.

Status
In development
Started
5 March 2026 (repository created)
Type

Source
muridabuhamed/CleverStudy

Overview

A student uploads a PDF and the application extracts its text, asks Google Gemini for key topics and a set of multiple-choice questions, and stores the result. From there the student can take a practice quiz, review flashcards, chat with an assistant that answers from the document, and annotate the PDF with highlights and bookmarks. Study sessions and quiz attempts feed a progress view.

The interface shows the product as "Smart Study Platform"; the repository and the name used here are CleverStudy.

Engineering challenge

An LLM turns free text into structured data only most of the time. Responses can arrive wrapped in code fences, in the wrong shape, or not at all when a quota is exhausted, and long documents do not fit comfortably in a prompt.

The application had to turn PDF text into reliable study material anyway, and stay usable when the model misbehaves.

Architecture and implementation

  1. UploadPDF files only, linked to the signed-in user.
  2. Extractpypdf reads the first 100 pages; the text is cached per file.
  3. AnalyzeThe first 20,000 characters go to Gemini, which returns topics and questions as JSON.
  4. ValidateCode fences are stripped, the structure is checked, and a parse failure yields empty results.
  5. StudyQuiz, flashcards scheduled with SM-2, and chat grounded in the document.

Frontend

React 19 and TypeScript built with Vite and styled with Tailwind CSS 4, organised by feature (auth, library, quiz, flashcards, annotations, profile). Each feature has its own pages and a small API module that calls the backend; the base URL comes from VITE_API_URL. The interface includes a PDF viewer with an annotation sidebar, a study timer, a progress tracker, light and dark themes, toast notifications and an error boundary.

Backend

FastAPI, layered into routes, services, repositories and domain models. A core module holds settings (pydantic-settings), logging and custom exceptions, and FastAPI dependency injection wires the pieces together. Authentication uses JWT with bcrypt password hashing. Data is stored in SQLite across nine tables: users, files, quiz attempts, flashcards, flashcard reviews, highlights, annotations, bookmarks and study sessions. Every file operation is checked against the signed-in user, and a file moves through pending, processing, completed and error states.

Deployment configuration

The repository includes a Render configuration for the backend (a web service with a persistent disk) and a Netlify configuration for the frontend. No live deployment is claimed here.

Key technical decisions

One class owns the model

All Gemini access sits in one GeminiClient class with three operations: analyse a document, chat with a document, and generate flashcards. Routes and services never touch the SDK, so the model, the prompts and the error handling can change in one place.

Fall back to a second model on quota errors

The client tries gemini-2.5-flash first and gemini-1.5-flash second. Quota errors move on to the next model; invalid-key errors and other failures stop immediately with distinct exceptions. Quota is detected by matching the error text, which is simple but depends on the wording of the SDK's messages.

Do not trust the model's JSON

The prompt asks for JSON only, but the client still strips code fences before parsing, checks that topics and questions are lists, and returns empty lists if parsing fails, so a malformed answer degrades the feature instead of crashing the request.

Bound the context, and know the cost

Analysis reads the first 20,000 characters of a document. Chat reads the first 15,000 characters plus the last four messages, each cut to 200 characters. That keeps responses fast and cheap, at the cost of ignoring the rest of long documents.

Spaced repetition with SM-2

Flashcard reviews update an ease factor, an interval and a repetition count with the SM-2 algorithm, then schedule the next review. A failed card resets to a one-day interval.

Current status and limitations

In development, with regular commits since March 2026.

  • 22 unit tests cover the authentication service and the user repository. The AI client and the quiz and flashcard services have no automated tests yet.
  • Long documents are only partly analysed because of the character limits above.
  • Some older modules from before the move to a feature-based layout are still in the repository.
  • SQLite on a single disk suits one instance; it is not a design for scaling out.
